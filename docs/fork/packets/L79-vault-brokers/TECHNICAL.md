# L79 technical design

Target design drafted against `2f385ee835`. Kyle authorized implementation and selected
OpenBao for encrypted storage. Packet-specific contracts still need implementation review.
Read the [foundation proposal](../LOOM-VAULT-FOUNDATION.md) for identity, storage, delivery,
permission ceilings and retry semantics; these constraints are not reimplemented per packet.

## Implemented enrollment boundary

Shared `vault-brokers.ts` contracts expose snapshot/begin/apply with access:read/access:write
scopes. `VaultBrokers` owns the encrypted CAS registry at
`environments/<sha256(environmentId)>/brokers`, capped at 64 machines, 16 live invitations,
128 events and 32 mutation receipts. Lifecycle/claim changes advance metadata revisions;
heartbeats only update presence and bounded activity. Four CAS attempts preserve concurrent edits.

Invitations bind protocol, environment, enrollment, fingerprint, nonce and ten-minute expiry.
The host proves its pre-generated Ed25519 key before a separate administrator approval. Normal
snapshots omit enrollment nonces. Proof HTTP is public-key authenticated under
`/api/loom/vault-brokers/{claim,challenge,heartbeat}` with 16 KB JSON limits. Heartbeat challenge
requests bind environment, machine, stable request ID and a timestamp within 30 seconds.
Challenges expire after 60 seconds and are single-use, with bounded process-local storage.
Service restart discards challenges; runners request another. Persisted disable is rechecked
before heartbeat CAS, and registry/audit write failure prevents success.

`BrokerIdentity` writes owner-only PKCS8 identity and connection files in a private directory
(default `~/.config/loom/vault-broker`), outside the current working tree. Symlinked identity
paths and public modes are rejected. The host private key is not encrypted by OpenBao; same-user
processes are inside its trust boundary. Connection origin/environment/machine are pinned.
`BrokerRunner` needs no administrator token or backend token, permits HTTPS or loopback HTTP,
rejects redirects and uses bounded responses/timeouts. It checks response identity bindings.

MCP management is restricted to full-access administrator clients. Calling threads cannot
enroll or approve themselves, regardless of their own Vault grants. CLI management calls the
same tools; the independent runner uses only signed proof HTTP. Web/desktop and mobile share
protected commands and gate on `vault-brokers`. They expose explicit refresh instead of
continuously polling. Presence changes require refresh. Provider adapters receive no keys or
new launch behavior in this slice.

## Managed user services and recovery

`BrokerService` owns host-local plan/install/start/stop/restart/status/uninstall through the
existing process runner, filesystem and host references. Existing upstream background-service
helpers are specific to the whole T3 server and its updater; they are not an independent broker
registration point. The fork service uses its own launchd label `com.loom.vault-broker` and
systemd unit `loom-vault-broker.service`, leaving the server's service unchanged.

The installed executable must be an absolute runnable Loom launcher. Descriptors pass arguments
directly, escape XML/systemd substitutions and contain no bearer tokens, private keys or personal
SSH-agent settings. A stable working directory in the service-definition folder avoids treating
the identity's home directory as a project. Installation enables next-session startup and requires
an explicit start now. Existing definitions must match the pinned state-directory marker and
ownership checks; install refuses a different plan. Failed operations preserve the definition
for an explicit retry. Uninstall stops the owned service before removal and retains enrollment.
Commands control only the calling OS user's service domain and never enable linger or use sudo.

`BrokerDaemon` renews through the existing signed HTTP service. It atomically replaces one
owner-only bounded status file and emits a safe JSON observation. Outages, approval-pending,
expired challenges and sealed backend conditions retry every 60 seconds. Disabled identity,
invalid proof, unsupported mode or broker configuration/local-state denial is terminal after
startup. A terminal report exits successfully; systemd `Restart=on-failure` and launchd
`KeepAlive.SuccessfulExit=false` restart crashes, with a 30-second delay/throttle. Startup failures
before a report can be written remain nonzero and may retry under the manager. No missing
identity is regenerated by startup or inspection. Cancellation records stopped when possible.

Status uses manager observations and the last validated local report, without network renewal.
Missing/unsafe local identity is reported as unavailable; stop/uninstall still work against the
owned service definition and never recreate that identity.
It reports unknown on manager failures, independently checks autostart and Linux linger, and
marks reports stale after two minutes or their heartbeat expiry. `heartbeatCurrent` requires a
running managed process, a fresh online report and an unexpired presence lease. It is machine
presence, never workload-use readiness. Report source separates backend sealed/denied states
from broker/control-plane failures. Local custody is explicitly an owner-only plaintext key
file, with no interactive unlock. OpenBao unlock remains on the owning control plane.

macOS requires the user's GUI session; no pre-login service is promised. Linux includes Pi
systemd-user hosts, with actual availability and linger reported rather than assumed. Real
boot/logout and Linux/Pi host execution remain acceptance work. Service controls deliberately
run through the host CLI: web/mobile/MCP retain remote enrollment and disable management and
cannot install an OS service on a client machine. No provider-specific launch behavior, new
wire contract, dependency, migration or upstream seam is added.

## Overview

Enroll a host through a reviewed, expiring challenge, then issue a renewable machine identity held outside projects. A local broker exposes authenticated per-workload channels and obtains bounded use leases. Report boot, unlock, reconnect, disable and re-enrollment states explicitly.

## Contracts and authorization

Enrollment start/claim/approve/complete and machine list/disable/re-enroll are distinct operations. Broker handshake binds host, workload and protocol version; a local socket path alone is not proof of caller identity. Status never returns enrollment secrets.

Use packet-owned `loom.vault-brokers.*` RPC methods if Loom transport is needed; enrollment schemas
and signed workload-check/mediated-operation boundaries are implemented; broader delivery and
local-agent transports remain a design-review output. Return typed unsupported, locked, denied, conflict, expired,
unavailable and operation-failed outcomes as appropriate, including environment authorization
errors. Register protected methods in the fork permission map and use environment RPC commands.
Metadata visibility, item management and credential use are distinct rights.

## Server and storage

Implement services in fork-owned paths and keep HTTP/RPC/MCP handlers thin. All credential
access goes through the shared backend/broker adapter; the feature never reads a personal
password manager as a fallback.

Keep machine bootstrap material in a private service-owned location, rotate it after enrollment and exclude it from project clones. Use encrypted local cache only if an offline policy is selected. Pending challenges and identities have expiry and explicit cleanup.

## Clients and agent-facing tools

Place shared client state in client-runtime and surface it through web, desktop and mobile.
Gate on advertised Vault capability/version; disable unsupported operations without disabling
ordinary T3 behavior. Agent tools use `loom_vault_brokers_*` names if exposed and
return safe summaries or operation handles. An agent cannot approve its own access, export raw
values by default or widen the caller's existing T3 permissions.

## Performance and failure handling

Use bounded pages and operation-scoped updates. Never subscribe to secret payloads, poll every
item continuously or repaint an idle UI. Reconnect by operation ID and persisted revision;
mutation retries use stable idempotency keys. External effects run after durable acceptance and
reconcile partial completion. Evidence tests await receipts or Deferreds, not sleeps.

## Alternatives and integration review

Inspect CLI/service launch environments and desktop shell hydration. Keep broker startup independent of an Electron window; use a fork CLI registration rather than a second app-specific credential service.

Prefer existing registries over new upstream seams. A direct provider-specific secret path
would duplicate policy and is not the recommended design. Where the shared interface is absent,
report unavailable or implement the approved minimal extension independently; do not import
another packet's UI/service internals.
