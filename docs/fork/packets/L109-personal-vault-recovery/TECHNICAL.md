# L109 technical design

Status: Designing. All personal paths, local interfaces and RPCs below are **proposed**. Scope is pending [Kyle's priorities](../LOOM-PERSONAL-VAULT.md).

## Existing boundary and engine decision

Current `apps/server/src/fork/vault/OpenBaoStore.ts:186` and `VaultCore.ts:149` expose backend values to the server. `apps/server/src/fork/vault/OpenBaoStore.integration.test.ts:53` tests restored backend versions; `:149` preserves revocations already captured in the copy. Neither proves personal custody or discovers later revocations. [L88](../L88-vault-recovery/) owns that development/server recovery scope.

Read [L102's maintained-engine evaluation](../L102-personal-vault-custody/TECHNICAL.md#engine-format-and-keys): KDBX 4 is the first candidate, not a chosen engine. Recovery must open the **actual selected engine's format with its actual unlock/recovery factors**. Use its native key hierarchy, integrity, encrypted export, re-key and authority capabilities. Do not design a parallel recovery cipher, epoch-wrapper hierarchy, signed authority chain or custom archive protocol. Missing capabilities mean unsupported behavior or another reviewed maintained engine.

## Kit, backup and export custody

The kit describes engine/version, opaque Vault reference, required factors, format compatibility, known backup identity/date and offline instructions. Its sensitive contents are whatever the selected engine actually needs: for example the correct database password/composite-key components or its documented recovery key. Do not invent a universal Loom recovery secret that claims to reopen every engine. If the engine supports generating an independent recovery factor, use its supported generation/encoding and test vectors; otherwise document the actual factor custody and limitations.

Keep required factors independent of the infrastructure they unlock and separate from the encrypted backup by default. Device-bound convenience keys alone may not survive device loss. Verify a read-back/open exercise without sending the factors elsewhere. Personal clients/custody must be independently trusted from the development host and full-access same-user agents; a signed window or generic OS string store alone is insufficient. No factor, raw value or recovery secret goes through RPC/MCP, prompts, shell snapshots or Library.

Default exports are the engine's encrypted portable database/backup format. Preserve supported attachments, history, deletion information and conflict copies; report omitted/nonportable data, including OS-bound passkeys. Use engine-native consistent save/snapshot/export and integrity validation. Confirm the backup contains all data required for the selected recovery path by opening it independently; a successful file write is insufficient. Any outer backup catalog/coordination receipt is non-secret status, not additional encryption or proof of current authority.

Store independent copies outside the development host. Native removable-file/print/share destinations, temporary outputs, file protection and OS backup inclusion need inventory. No default clipboard or plaintext export. Removing one copy or retiring instructions cannot delete external files, photos or printer history. Kit replacement uses supported engine factor change/re-key, not a metadata "retired" flag pretending to invalidate a copied key.

## Local restore lifecycle

Proposed local responsibilities: prepare/verify kit, export/inspect backup, stage/inspect restore, cancel/close, and resume safely or create an isolated replacement. These are not existing API names. The independently distributed trusted client must operate without the original Loom server.

1. Confirm the clean client's installation trust and compatible maintained engine. Choose an empty isolated restore profile; obtain factors only on the trusted surface. Do not modify an existing Vault in place.
2. Use the engine's bounded parser, KDF and integrity checks to open the native backup. Reject wrong factors, tampered/truncated/unknown formats, unreasonable resource demands and unsupported versions without overwriting existing data. Do not execute imported content or trust archive paths where the engine uses an archive.
3. Inspect recovered content, supported history/deletions/attachments, conflict copies and missing/unsynced data inside the trusted client. Disable sync and all external grants/sessions while status is unreconciled. Readable content is not current authority.
4. Reconcile according to the selected engine and loss cases below. Only a verified supported transition may resume access; otherwise create a separately initialized/re-keyed replacement through engine-native operations and keep the old copy isolated. Record local operation outcomes for crash recovery, not crypto authority.
5. Cancel/close clears decrypted buffers/use handles and controlled staging files. Report cleanup failures. After committed engine re-key or storage cutover, inspect and repair forward rather than silently restoring obsolete factors or permissions.

| Loss case                                                | Data recovery                                                                                                                                                     | Required reconciliation                                                                                                                                                                             |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server lost; trusted device survives                     | Use its native encrypted cache/export or independent backup.                                                                                                      | Compare available current engine/storage evidence; rebuild relay separately. Personal unlock cannot require server unseal.                                                                          |
| One device lost                                          | Use a surviving trusted client to revoke supported sync/storage credentials and perform engine-native re-key where needed; enroll replacement by supported means. | Copied complete database keys still unlock old copies. Independent device encryption revoke is unsupported where the engine lacks it.                                                               |
| All devices lost; factors and independent backup survive | Open native backup offline on a clean compatible trusted client, initially isolated.                                                                              | Restore current storage/authority state only with independent current evidence and supported engine facilities. Otherwise keep isolated or initialize/re-key a replacement with new storage access. |
| Stale complete database and no reliable latest evidence  | Recover backed-up content, including possible obsolete data/permissions; inspect data loss.                                                                       | Treat current revocations/authority as unknown. Never automatically merge/publish the old file or replay grants. A replacement does not disable the old Vault elsewhere.                            |
| Kit/factors lost; current trusted client still usable    | Use supported factor-change/re-key/export to prepare and independently verify replacement recovery material.                                                      | Some engine/hardware modes cannot regenerate missing factors; show unsupported. Old stolen backups/factors may remain usable.                                                                       |
| No usable factors, trusted copy or required ciphertext   | Identify exactly what is missing.                                                                                                                                 | Unrecoverable for that data; server administrator access is not an unlock bypass.                                                                                                                   |

## Authority, revocation and stale restore

Use only the chosen engine's real device/recovery/authority facilities. For KDBX-style whole-database custody, the database key is not a per-device membership system. Storage credential revocation controls future transport where enforced; it cannot make a lost device forget a copied database key. Supported database re-key can protect suitably re-encrypted future files, but cannot revoke historical copies. Do not describe native deleted-object metadata, a timestamp, a digest or a local receipt as a cryptographic revocation frontier.

A valid old database may restore obsolete items, permissions or custom metadata. Restored permissions are historical data only, never executable authorization. Disable imported development grants, broker enrollments, provider sessions, scheduled access and agent approvals until current services explicitly authorize them. If those systems also lost their current state, do not infer it from the personal archive.

Compare independent current engine/storage evidence if available. If there is no reliable freshness evidence, report authority-unknown and avoid automatic old-identity resumption. A new separately initialized/re-keyed engine database and fresh supported sync credentials can establish a replacement without reviving the old storage access, but old copies/Vaults may remain alive elsewhere. Do not claim a replacement cryptographically rejects old device signatures unless that engine actually has and verifies such a mechanism.

Record engines may supply richer revocation/recovery semantics; verify those exact APIs and failure cases before advertising them. Outer non-secret coordination receipts can record observed outcomes, never add missing authority guarantees. No external freshness witness is assumed. Offline recovery and clock rollback cannot discover new revocations or extend valid authority.

Downstream website/API credentials recovered from an old backup may already be compromised or changed. Show repair/issuer-side rotation work through [L87](../L87-vault-lifecycle/) and [L110 maintenance](../L110-personal-vault-maintenance/) where supported; unsupported issuers need explicit manual repair. Recovering or re-keying a database does not revoke a copied provider credential.

## Proposed metadata contracts and gates

Only if host coordination is useful, proposed `packages/contracts/src/fork/personal-vault-recovery.ts` and `apps/server/src/fork/personal-vault-recovery/` hold safe status/receipts. The host never receives factors, local file paths, archive plaintext or decryption keys.

| Proposed non-streaming RPC                        | Payload / success                                                                                    | Gate                                                                                                                    |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `loom.personal-vault-recovery.status`, `.inspect` | Opaque Vault/operation ID; safe phase, observed engine/storage version, verification/cleanup outcome | `AuthAccessReadScope` plus metadata visibility and operation ownership                                                  |
| `.recordReceipt`                                  | Operation ID, expected receipt revision and non-secret client result; persisted coordination receipt | `AuthAccessWriteScope` plus proven caller/operation ownership; does not authenticate recovered data or confer authority |
| `.cancel`, `.close`                               | Owned operation ID and expected receipt revision; coordination outcome                               | `AuthAccessWriteScope` and ownership; cannot retract external exports or assert native erasure                          |

Errors include `EnvironmentAuthorizationError`, unsupported, denied, invalid-input, conflict, unavailable and outcome-unknown. Local engine outcomes distinguish wrong factors, invalid format/integrity, incomplete data, locked, clock uncertainty, authority unknown and cleanup needed without leaking contents. Use matching fork permission maps, thin handlers and `createEnvironmentRpcCommand`/`permissionAtom`. Environment grants never unlock the personal engine. Native cancellation is complete only when the trusted client/engine acknowledges its outcome.

Proposed MCP/CLI `_status`, `_inspect`, `_cancel`, `_close` tools under `loom_personal_vault_recovery_*` expose only the same authorized metadata/outcomes and owned coordination. No kit creation, factor reveal, export, decrypt or restore-promotion tool. All providers and scheduled agents use the same service gates. Command-only jobs remain unsupported until a suitable independent broker exists.

## Storage, clients and performance

Proposed host `fork_personal_vault_recovery_receipts` stores opaque IDs, owner, request digest, expected coordination revision, safe phase and sanitized outcome; uniqueness/indexes support owner-scoped idempotency and bounded retention. Packet migration IDs start at 1; no schema change occurs here. No custom encrypted backup table or archive format is introduced.

Native engine backups/staging stay in trusted private storage or the user's explicit independent destination. Proposed host status/launch adapters live in `packages/client-runtime/src/fork/personal-vault-recovery.ts`, `apps/web/src/fork/personal-vault-recovery/` and desktop/mobile `src/fork/personal-vault-recovery/`. Native recovery packaging, file custody and exact build targets remain unknown until inventory.

Gate optional host status on proposed `personal-vault-recovery` in `capabilities.loomFeatures` and independently check the actual engine/native recovery mode. Missing server support must not disable a supported installed offline recovery client. Bound metadata pages to 50/64 KiB provisionally; stream large engine-native backups with bounded buffers where supported. Measure KDF/memory costs on iPhone and large-database/attachment saves without replacing engine integrity or format rules. No secret progress strings or idle animation.

## Overlap and alternatives

[L102](../L102-personal-vault-custody/) owns maintained-engine/custody evaluation; [L103](../L103-personal-vault-library/) owns item/history semantics; [L104](../L104-personal-vault-imports/) owns reviewed migration/portable export mapping; [L107](../L107-personal-vault-native/) records OS-bound credential limits; [L106](../L106-personal-vault-agents/) owns delegated-session revocation. [L108](../L108-personal-vault-sync/) consumes the same proven engine facilities, but L109 local recovery must work without its relay or UI.

L88 recovers development OpenBao, policy and infrastructure without personal factors. It may retain a personal relay's ciphertext if configured, but cannot decrypt or attest current personal authority. L109 recovers personal data without L88. Neither packet depends on the other's internals or creates a circular recovery requirement.

Reject server-side factor entry, a universal custom recovery secret/archive, grants restored verbatim, the only kit beside the only backup, and administrator-password bypass. Any plaintext human export needs explicit product scope and a trusted native destination, never a general RPC/MCP path.
