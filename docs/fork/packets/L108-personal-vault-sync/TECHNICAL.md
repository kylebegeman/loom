# L108 technical design

Status: Designing. All personal paths and APIs below are **proposed**. Scope is pending [Kyle's priorities](../LOOM-PERSONAL-VAULT.md).

## Existing boundary and engine decision

Current `apps/server/src/fork/vault/VaultCore.ts:149` returns a loaded value in the server; `apps/server/src/fork/vault/OpenBaoStore.ts:186` reads backend payloads into that process. `Redacted` limits accidental rendering, not server access. Current `packages/contracts/src/fork/vault-core.ts:104` methods are development Vault APIs, not personal sync. Existing Electron safeStorage and mobile SecureStore wrappers do not establish isolation from full-access same-user agents.

[L102 custody](../L102-personal-vault-custody/TECHNICAL.md#engine-format-and-keys) evaluates maintained engines/formats, with **KDBX 4 as the first candidate, not a selection**. L108 must use the selected engine's actual key hierarchy, encrypted format, integrity, merge and synchronization capabilities. No custom per-record cipher, key hierarchy, signature-chain protocol or replacement synchronization engine is selected here. Missing capabilities mean explicit unsupported behavior or a different reviewed maintained engine, never a home-grown substitute.

## Custody, encrypted cache and offline unlock

The personal client/custodian must be independently trusted from the development host and its agents. Separate OS principals/devices are the proposed safe baseline. Signed code, a separate window, file permissions, a biometric prompt or safeStorage availability alone do not prove resistance to arbitrary same-user code. Keep unlock unavailable on an unproven topology; use an independently trusted device where supported.

Persist only engine-produced encrypted data, including sensitive labels, history and supported attachment/deletion information. Any proposed cache namespace, such as `loom:personal-vault-sync:cache:v1`, identifies local storage only and is not a new cryptographic format. Device unlock protects exactly the selected engine's required unlock material through reviewed native custody. No personal key, factor or raw value goes through ordinary environment RPC/MCP, prompts, shell snapshots, Library or host query persistence.

Lock on explicit action, configured inactivity, sleep/background and supported session invalidation. Clear decrypted views and local use handles; managed-runtime zeroization and OS screenshot erasure are not guaranteed. Use the engine's crash-safe save before reporting offline edits durable. Storage-full/eviction errors distinguish saved encrypted data from unsaved work. Cache removal reports unsynced loss and does not imply deleting remote copies.

## Reconnection, conflict and deletion requirements

Before upload, inspect current storage authorization and any freshness evidence the selected engine actually provides. Transfer with its supported conflict detection or a storage compare-and-swap when available. Outer operation IDs/digests deduplicate transfers; they establish storage outcomes, not authenticated personal history. Do not overwrite either complete file or record set after an unexplained version change.

Whole-database sync preserves both encrypted files on a race. Use engine merge rules only after testing password conflicts, attachments, history and deletion-versus-edit on the chosen implementation. If a safe merge is unavailable, require explicit trusted-client conflict-copy inspection and replacement; never silently choose a file by wall-clock timestamp. Engine timestamps used internally by a merge are not proof of current authority.

Track deleted items and engine-native tombstones/deletion metadata where supported. Test an old complete database returning after deletion: it may still contain the item and old permissions. Do not automatically publish that copy or claim cryptographic anti-resurrection. Require reviewed reconciliation, retained conflict copies or full resync; if supported primitives cannot preserve the required deletion semantics, disable automatic reconciliation and show the limitation. Retention/pruning follows the engine's supported rules and tested policy; no invented checkpoint makes deletion permanent across arbitrary old copies.

For record engines, exercise their native concurrent-edit and deletion behavior, including retention expiry and re-enrollment/full-resync rules. An engine-specific adapter may normalize safe status, but cannot add cryptographic capabilities by changing labels.

## Pairing, revocation, rotation, clocks and rollback

Pairing uses the selected maintained engine's supported admission/transfer workflow plus the independently trusted personal boundary. Verify the intended Vault and destination on trusted surfaces, inspect/cancel/expire pending work and avoid exposing key material in QR snapshots. Where only database-key sharing exists, describe it as shared-key access; do not advertise independently revocable device encryption. Missing secure admission support is unsupported.

Revoke supported sync/storage credentials and local sessions, then use engine-native key change/re-key where future ciphertext must exclude a lost device. Verify the new database with the new factors before cutover, retain a controlled recovery copy and inspect interrupted re-key state before retry. Never automatically fall back to the old key/file after committed cutover. For a record engine, use only its implemented rotation/device revoke semantics. Re-pairing establishes fresh supported device access, not reactivation of a revoked storage credential.

A disconnected device may keep reading a complete database with its copied key. Online revocation cannot erase those copies; changing keys protects only suitably re-encrypted future data. Offline edits from a removed device are held for trusted reconciliation, not accepted because their timestamp predates removal. If an engine cannot prove when an offline edit was authorized, report that uncertainty.

Show the approved offline policy and last actual check. A trusted elapsed-time source may enforce a local lock deadline, but wall-clock changes/restart without continuity must not extend it. This is local policy, not cryptographic expiry of a KDBX key. If the platform cannot enforce it, report unsupported enforcement. Rollback of a valid complete database may pass engine integrity: compare independently retained known versions where available, preserve unexpected copies and show freshness unknown when evidence is absent. No engine-independent signed sequence, revocation frontier or universal hostile-relay detection is assumed. [L109](../L109-personal-vault-recovery/) covers stale restore.

## Proposed contracts and services

An engine may already supply its sync transport. Only if needed, proposed schemas in `packages/contracts/src/fork/personal-vault-sync.ts` and a proposed relay service in `apps/server/src/fork/personal-vault-sync/` carry opaque engine ciphertext and coordination receipts. They do not implement encryption or claim authority the engine lacks.

| Proposed non-streaming RPC                    | Payload / result                                                                                                          | Gate                                                                                                            |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `loom.personal-vault-sync.status`, `.inspect` | Opaque Vault/operation reference; safe phase/counts, known storage version, sanitized outcome                             | `AuthAccessReadScope`, explicit personal metadata visibility/operation ownership                                |
| `.fetchCiphertext`                            | Supported adapter/version, opaque object/version, bounded cursor; engine ciphertext                                       | `AuthAccessReadScope` plus proven personal/storage access; not an agent tool                                    |
| `.storeCiphertext`                            | Operation ID, supported adapter/version, expected storage version and opaque engine ciphertext; accepted/conflict receipt | `AuthAccessWriteScope` plus proven personal/storage access; no claim that receipt authenticates engine contents |
| `.cancel`, `.close`                           | Owned operation ID and expected receipt revision; actual coordination outcome                                             | `AuthAccessWriteScope` and ownership; cannot undo accepted file writes or engine operations                     |

Errors include `EnvironmentAuthorizationError` plus unsupported, locked, denied, conflict, invalid-input, quota, unavailable and outcome-unknown. Trusted local engine outcomes also distinguish integrity failure, clock uncertainty and unknown freshness. Unlock and engine key change remain local; no raw secret or factor field exists on these RPCs. Timeouts require receipt inspection before retry.

Use existing fork permission maps, thin handlers and `createEnvironmentRpcCommand`/`permissionAtom`; environment authorization is an outer ceiling, not personal unlock authority. The shared personal extension is proposed, not implemented. Consume proven primitives individually and degrade on absence.

## Storage, clients and performance

Proposed relay tables `fork_personal_vault_sync_objects` and `_receipts` hold opaque object/storage versions, operation owner, mutation ID/digest and sanitized status. Unique operation identity supports retries; indexes scope pages by owner/object/version. Engine ciphertext files, if this adapter needs them, live under `<stateDir>/fork/personal-vault-sync/` with atomic replacement/conflict-copy retention and bounded orphan cleanup. Packet migration IDs start at 1; no schema change occurs during design. Do not put personal plaintext or keys in OpenBao records.

Proposed shared state: `packages/client-runtime/src/fork/personal-vault-sync.ts`; status/launch adapters: `apps/web/src/fork/personal-vault-sync/` and desktop/mobile `src/fork/personal-vault-sync/`. Browser/native custody packages and seams require inventory. These are proposed locations, not ready dependencies.

Gate optional relay UI on proposed `personal-vault-sync` in `capabilities.loomFeatures`, and separately verify engine/native capabilities. Missing relay support preserves already supported trusted offline use; missing custody prevents unlock. Provisional metadata pages are 50 entries; stream large encrypted database files with bounded buffers, cancellation and resumable transfer only where transport permits it. Whole-database sync has file-size/write-amplification costs; measure realistic databases/attachments and coalesce saves rather than upload per keystroke. No secret subscriptions or idle repainting.

## Agent-facing tools and overlap

Only proposed `loom_personal_vault_sync_status`, `_inspect`, `_cancel` and `_close` may expose authorized metadata/outcomes and owned coordination. All providers and scheduled agents use the same service gates; no ciphertext exports, keys or personal values enter their outputs. Command-only jobs remain unsupported until a suitable independent broker exists.

[L102](../L102-personal-vault-custody/) evaluates custody/engines; [L103](../L103-personal-vault-library/) owns item/history semantics; [L104](../L104-personal-vault-imports/) owns reviewed import/export; [L105](../L105-personal-vault-browser/) and [L107](../L107-personal-vault-native/) consume supported trusted caches; [L106](../L106-personal-vault-agents/) owns delegated sessions. [L79](../L79-vault-core/), [L81](../L81-vault-grants/) and [L85](../L85-vault-delivery/) remain development patterns/gates; [L87](../L87-vault-lifecycle/) owns downstream credential rotation. L109 restores locally without this relay; [L88](../L88-vault-recovery/) restores infrastructure without personal unlock keys. These are overlap boundaries, not mandatory packet dependencies.
