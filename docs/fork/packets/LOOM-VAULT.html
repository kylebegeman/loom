V01 · L72 · Medium effort · High impact

Headless readiness checks

Prove an environment can perform its configured unattended work before launching a task.

Product details and design questions

How it works

Run bounded checks inside the actual broker or runner context. Resolve profile requirements, verify unlock and grant state, and exercise harmless provider-specific operations such as repository reads. Classify authentication, authorization, network, host-trust and missing-tool failures separately; record check time and environment identity.

User experience

Open Vault readiness from the environment, project, command palette or task preflight. See a concise result with a repair action for each failure, retry a single check, or cancel an active run. A stale successful check is visibly stale.

Product value

Prevents a terminal login from being mistaken for proof that a background runner is ready.

Dependencies and opportunities

Uses shared inspection and connector-check interfaces. Can check existing GitHub setup before Vault migration; absent optional adapters report unsupported, not success. Unlocks preflight for schedules and newly enrolled machines.

Open decisions

  • Which checks block a launch versus warn, and what freshness window is acceptable?
  • Should scheduled tasks require preflight by default or only when their profile requests it?

V02 · L73 · Medium effort · High impact

Searchable credential references everywhere

In progress: environment search/copy and profile pickers work locally. Composer attachments and wider consumers remain selected.

Attach named Vault items without copying their values into prompts or settings.

Product details and design questions

How it works

Open decisions

V10 · L81 · Large effort · High impact

SSH key management and Loom SSH agent

Use dedicated Loom-managed SSH keys for development connections and Git operations.

Product details and design questions

How it works

Generate or explicitly import keys, keep private material behind the broker signing interface, and track public-key registrations and host trust independently. Give workloads a restricted identity set through platform-appropriate agent transport. Validate destination constraints using supported SSH mechanisms or a mediated connection, not an assumed hostname in generic signing requests.

User experience

Create a development key, copy its public key, register it on selected hosts, test access and replace or revoke it. A changed host key is a separate reviewed trust action. Personal 1Password settings remain untouched.

Product value

Directly addresses repeated personal key-manager approvals while retaining SSH workflows.

Dependencies and opportunities

Uses storage, broker and policy interfaces plus SSH adapters. Account connectors may automate public-key registration when available; otherwise provide explicit manual registration. Unlocks remote workers and optional future commit signing.

Open decisions

  • Generated keys and host pins use Ed25519; imports and further algorithms remain open.
  • D7: The implemented slice uses mediated host-bound connections with no forwarding. General runner sockets and Windows transports remain open.
  • Is commit signing part of a later extension of this packet? It is not required by the current SSH outcome.

V15 · L86 · Massive effort · High impact

Credential lifecycle automation and short-lived access

Issue temporary access and rotate long-lived credentials without losing track of consumers.

Product details and design questions

How it works

Adapters issue expiring credentials or certificates where supported. Rotation prepares a replacement, validates selected consumers, cuts over bindings, then retires the old version when the provider permits overlap. Track partial results and reconcile retries; providers allowing only one valid secret require an explicit interruption strategy.

V16 · L87 · Large effort · High impact

Backup, recovery, and portability

Make the self-hosted Vault recoverable and movable without losing access control.

Product details and design questions

How it works

Create encrypted consistent backups covering payloads, metadata and required policy state. Keep recovery material separately managed. Restore into an isolated destination, verify decryption and policy integrity, then explicitly promote it with old-machine trust reviewed or invalidated.

User experience

See last verified recovery, download an encrypted export, perform a recovery exercise and move servers through a reviewed workflow. Lost-device recovery shows what access can be disabled and what downstream credentials need rotation.

Product value

Preserves ownership and makes Vault dependable as a shared infrastructure dependency.

Dependencies and opportunities

Uses backend snapshot/export, key-custody and machine-revocation interfaces. Builds on the minimum restore capability required by ext-vault rather than postponing all backups. Unlocks server migration and future hosting changes.

Open decisions

  • D9: Choose backup destination, retention, recovery owner and acceptable recovery time/data loss.
  • How is authoritative revocation state recovered when the original server and its latest log are unavailable?
